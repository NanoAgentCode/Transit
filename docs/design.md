# 仓渡 RepoTransit：私有仓库文件上传客户端设计文档

状态：已据此实现首版客户端（2026-09-28）。GitHub 私有仓库授权和小文件上传已现场验证；Gitee 授权与上传、两个平台的令牌刷新仍需现场验证。

## 1. 目标与边界

开发一个 Windows 桌面客户端，将拖入的本地文件上传到用户有写入权限的 GitHub 或 Gitee 私有仓库。客户端支持配置多个平台账号凭据和多个目标仓库，并以 `YYYY-MM/原文件名_时间戳.扩展名` 组织文件。

本工具仅供本人及拥有仓库访问权的用户使用。它不提供公开图片直链、匿名访问、图片处理、远端文件管理、自动同步或团队权限管理。第一版不部署自有服务。

完成标准：用户在首次授权并配置仓库后，能够选择目标仓库，拖入文件，看到逐项结果；成功文件位于预期分支、月份目录和文件名下，并能复制仓库文件页链接或仓库内路径。

## 2. 已确定的需求

| 项目 | 规则 |
| --- | --- |
| 平台 | GitHub、Gitee |
| 仓库可见性 | 私有仓库 |
| 客户端 | Windows 常规窗口程序 |
| 输入 | 拖入一个或多个任意类型的本地文件；可附带“选择文件”按钮，便于无拖拽环境使用 |
| 目标 | 多个账号凭据、多个仓库；上传前可切换目标，并设置默认目标 |
| 目录 | 按上传时本机所选时区的年月划分，格式 `YYYY-MM/` |
| 文件名 | 原文件主名、时间戳、原扩展名，例如 `示意图_20260924T153012345.png` |
| 输出 | 每项上传状态、失败原因、私有仓库文件页链接、仓库内路径 |
| 凭据 | 浏览器完成平台授权；访问令牌保存在本机安全存储中 |

时间戳采用 `yyyyMMdd'T'HHmmssfff`，默认使用 Windows 当前本地时区。扩展名保留原样；无扩展名文件同样可上传。若生成路径已存在，依次追加 `_2`、`_3`，不得覆盖远端文件。一个批次中的每个文件独立报告结果，不因单项失败取消其他文件。

## 3. 用户流程

### 3.1 首次配置

1. 在“账号与授权”中选择 GitHub 或 Gitee，按平台流程在系统浏览器中授权。
2. 客户端取得令牌，查询账号身份；凭据验证失败时不保存为可用状态。
3. 在“仓库”中选择或填写已有仓库，确认可访问、目标分支存在且可写。
4. 可重复关联账号和仓库，并指定一个默认上传目标。

客户端不负责创建仓库。Gitee 的首次配置还需用户注册自己的第三方应用，并在本机填写 Client ID 与 Client Secret；不得把一组共享密钥硬编码进分发包。

### 3.2 上传

1. 主窗口显示当前平台、账号、仓库和分支；用户可切换目标。
2. 用户拖入文件，窗口列出文件、目标路径及总大小；确认后开始上传，避免拖错仓库。
3. 客户端逐项计算目标路径、检查是否已存在、上传并展示“等待中／上传中／成功／失败”。
4. 成功项可复制仓库文件页链接或仓库内路径；失败项可单独重试。

私有仓库链接仅供已登录且有权限的账号访问，不承诺能嵌入公开网页。

### 3.3 管理配置

可新增、重命名本地显示名称、重新授权、断开账号；可新增、编辑、删除本地仓库配置及更改默认目标。删除本地配置不删除远端文件；断开账号时删除本机保存的相关令牌，并将依赖它的仓库标记为待授权。

## 4. 界面设计

主窗口只包含目标选择、拖拽区、待上传列表、上传按钮、结果列表和“设置”入口。设置窗口分为“账号与授权”和“仓库”两页。令牌与 Client Secret 不回显明文，仅显示授权状态、账号和到期信息（若平台返回）。

上传结果需明确区分网络失败、授权失效、无写入权限、分支不存在、文件过大、远端路径冲突及平台限流。对可重试错误提供重试入口；对授权失效提供重新授权入口。

## 5. 技术方案

### 5.1 客户端结构

实现采用 .NET/WPF 窗口与独立的核心类库：`界面 → 上传协调器 → GitHub/Gitee 适配器 → 平台 API`。认证、仓库配置、命名与路径生成、上传结果各自独立；具体模块边界见 [架构与维护指南](architecture.md)。

本地配置保存平台、账号标识、仓库 owner/name、分支、默认目标及凭据引用；不保存明文令牌。访问令牌、刷新令牌和用户自行配置的 Gitee Client Secret 使用 Windows Credential Manager 或同等级的用户级安全存储。日志不得记录令牌、授权码、完整请求头或带凭据的 URL。

### 5.2 GitHub 授权

第一版拟采用 GitHub OAuth 应用的设备授权流程：客户端打开 GitHub 授权页并显示一次性验证码；用户在浏览器确认后，客户端按服务端返回的间隔轮询领取令牌。此流程无需在桌面程序中嵌入应用密钥，但注册的 OAuth 应用需启用设备授权。随后查询可访问仓库，并在选定仓库上验证写入能力。

GitHub OAuth 的仓库权限粒度与 GitHub App 不同；如果需要把授权限制到单一仓库，应在实现前评估改用 GitHub App。第一版不得将“选择上传仓库”误称为“令牌只可访问该仓库”。

### 5.3 Gitee 授权

第一版拟采用 Gitee 授权码流程：系统浏览器打开授权页，用户确认后，客户端通过注册的回调地址取得授权码，使用用户自己的 Client ID、Client Secret 换取访问令牌。Gitee 官方文档中的换令牌请求包含 `client_secret`，并描述了到期后使用刷新令牌的流程；客户端需保存并更新令牌，刷新失败则提示重新授权。

实现前的验证门槛：使用真实的个人 Gitee 第三方应用确认本机回调地址是否可注册、授权回调是否可由桌面客户端接收、所需权限范围和刷新行为。若本机回调不可用，优先评估文档支持的 WebView 回调；仍不可行时，不把 Gitee 浏览器授权标为已完成，而应重新确定接入方式。

### 5.4 仓库与凭据关系

一个账号凭据可以关联多个仓库；一个仓库配置只引用一个凭据。不同平台和账号的凭据互不混用。仓库配置包括平台、账号、owner、仓库名、分支、本地显示名称与默认状态。默认目标全局最多一个；没有默认目标时上传前必须选择。

### 5.5 上传与命名

路径由上传当时的年月及原文件名生成，例如 `2026-09/示意图_20260924T153012345.png`。保留中文和空格，向平台 API 发请求时按路径段正确编码。检查路径已存在后才上传；若平台仍报告冲突，重新生成序号再试，绝不覆盖已有内容。

每个文件一次上传提交。客户端限制并发数，遵守平台 API 的限流响应；取消操作只停止尚未提交的文件，已成功提交的文件不自动回滚。失败重试沿用同一目标仓库，但重新检查远端路径，避免覆盖。

第一版最大单文件体积须在真实 API 验证后确定并在界面提前拦截；不要在未验证前承诺上传任意大小文件。

## 6. 数据与安全

本地配置建议用 JSON 保存非敏感字段，以稳定 ID 关联安全存储中的凭据。程序启动时校验引用；缺失令牌的仓库显示“待授权”。令牌刷新应原子替换旧值，失败时保留可诊断状态而不输出秘密。所有平台请求使用 HTTPS，超时和重试次数有上限。

授权仅请求上传所需权限。断开关联清除本机凭据；若用户希望在平台端撤销授权，界面提供相应平台的授权管理入口并说明本地删除不等于远端撤销。

## 7. 异常与边界

| 场景 | 处理 |
| --- | --- |
| 未关联账号或仓库 | 引导进入设置，禁止开始上传 |
| 私有仓库无权限或分支不可写 | 保留文件在队列中，显示具体原因，不尝试其他仓库 |
| 授权取消、过期或被撤销 | 停止该凭据的后续上传，提示重新授权 |
| 网络中断、超时、限流 | 保留失败项；按有限次数退避重试或由用户手动重试 |
| 同名或时间戳碰撞 | 追加序号，确认新路径后上传 |
| 文件在排队期间被移动或修改 | 开始上传前重新读取并提示变化；失败项不得显示成功 |
| 多文件部分成功 | 逐项展示结果，成功项不回滚 |
| 非图片文件 | 与图片使用同一上传流程，不按扩展名过滤，也不进行格式转换 |

## 8. 开发步骤与验证

1. 建立项目骨架与本地配置模型；检查是否需要初始化 codegraph。
2. 先编写命名、目录、路径冲突、配置关联和错误映射的用例，再实现对应逻辑。
3. 实现 GitHub 授权与上传适配器，用测试私有仓库验证真实上传、链接与权限。
4. 验证 Gitee 授权前提，再实现 Gitee 适配器，并在测试私有仓库验证令牌刷新和上传。
5. 接入拖拽界面、批量状态、目标切换和配置管理，完成 Windows 打包。
6. 更新 README 和 `docs` 使用说明；检查无明文凭据、无越界改动。

验收至少覆盖：两个平台各一个私有仓库、一个账号关联多个仓库、多个账号切换、默认目标切换、图片及非图片文件、中文及特殊字符文件名、无扩展名文件、路径碰撞、批量部分失败、授权失效、网络失败、重新授权和断开关联。

## 9. 待确认的产品细节

这些选择不阻止方案评审，但应在界面定稿前确定：

- 是否允许把目录前缀配置为 `images/YYYY-MM/`；当前按仓库根目录下的 `YYYY-MM/` 设计。
- 上传后复制操作默认使用文件页链接还是仓库内路径；当前同时提供两者。
- 上传前是否始终显示确认列表；当前为防止误传到私有仓库，设计为需要确认。
